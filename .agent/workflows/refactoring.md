# Инструкция: Архитектурный рефакторинг и аудит

Ты выступаешь в роли Senior Software Architect. Твоя цель — проанализировать кодовую базу и составить план рефакторинга, который обеспечит масштабируемость и стабильность проекта.
Проанализируй проект и составь документ что самое важное следует сделать рефакторинг, чтобы код код лучше работал, лучше поддерживался, лучше читался. Самое важное выдели что следует сделает.

## 1. Процесс анализа (Audit Steps)

Перед предложением правок ты должен провести аудит по следующим критериям:

### 1.1. Соблюдение Feature-Based структуры
* Проверь, не раздута ли папка `/components`. Если компонент используется только в Календаре, он должен быть перенесен в `/features/calendar/components`.
* Проверь наличие "циклических зависимостей" между фичами.

### 1.2. Чистота логики (Logic Separation)
* Найди компоненты, где бизнес-логика (сложные расчеты, фильтрация статусов) смешана с JSX.
* Выдели логику, которую можно вынести в кастомные хуки в папку `/hooks` или `/features/[name]/hooks`.

### 1.3. Технический долг TypeScript
* Найди и предложи заменить все типы `any` на строгие интерфейсы.
* Проверь соответствие типов данных из Supabase и локальных интерфейсов.

### 1.4. Оптимизация производительности
* Проверь использование `useEffect` для загрузки данных. Предложи переход на `TanStack Query` там, где это еще не сделано.
* Найди тяжелые вычисления (например, аналитика финансов), которые требуют `useMemo`.

## 2. Формат отчета по рефакторингу

Результатом твоей работы должен быть документ со следующей структурой:

### 2.1. Top Priorities (Самое важное)
Выдели 3–5 критических изменений, которые дадут максимальный эффект для стабильности системы.

### 2.2. Таблица проблемных зон
| Приоритет | Файл / Модуль | Описание проблемы | Что сделать |
| :--- | :--- | :--- | :--- |
| 🔴 High | `AbonementForm.tsx` | Слишком длинный компонент (500+ строк) | Разбить на мелкие UI-компоненты и вынести логику в хук |
| 🟡 Medium | `/lib/supabase.ts` | Устаревшие типы данных | Обновить типы через CLI Supabase |
| 🔵 Low | `Header.tsx` | Лишние ре-рендеры | Обернуть в `React.memo` |

### 2.3. План реализации (Step-by-Step)
Опиши последовательность действий, чтобы рефакторинг не сломал работающий функционал (согласно правилу "Без причины не удалять рабочий функционал").

## 3. Правила «Чистого кода» для проекта

При проведении рефакторинга всегда следуй этим принципам:
1. **DRY:** Если расчет списания средств дублируется в двух местах — создай единую утилиту в `/lib`.
2. **Early Return:** Перепиши вложенные `if/else` на Guard Clauses.
3. **Naming:** Убедись, что названия переменных соответствуют бизнес-домену проекта.
4. **Formatting:** Все новые решения должны соответствовать стандартам в rules `formatting-data.md`.
