# Разработка панели администратора SaaS-платформы (Admin Panel)

Этот навык описывает стандарты и архитектурные паттерны для создания профессиональной, безопасной и масштабируемой панели администратора в SaaS-продуктах. Панель предназначена для управления пользователями, организациями, подписками и анализа ключевых метрик продукта.

---

## 1. Архитектура базы данных и безопасность

Панель администратора обладает высшим уровнем доступа, поэтому безопасность должна быть реализована на всех слоях.

### А. Таблицы организаций и пользователей (Multi-Tenancy)
Основа SaaS — это мультиарендная архитектура, где пользователи принадлежат к организациями (тенантам).
*   **`organizations`**: хранит данные о компаниях/клиентах, их тарифах (`subscription_plan`) и кастомных лимитах (`limits`).
*   **`organization_members`**: связующая таблица пользователей и организаций с указанием роли внутри организации.

### Б. Глобальные роли (Динамический RBAC)
В системе используется динамический Role-Based Access Control (RBAC). 
*   Названия ролей могут быть любыми (кастомными), они создаются и настраиваются динамически. Главное — это наличие необходимых `role_permissions` у пользователя.
*   Доступ к конкретным разделам админ-панели (или к админке в целом) должен проверяться исключительно по наличию соответствующих прав (например, `admin:access`, `billing:manage`), а не по жестко заданному имени роли.

### В. Защита БД через RLS (Row Level Security)
Все административные таблицы и критичные функции должны быть защищены политиками RLS.
*   Доступ на чтение/изменение системных логов, биллинга и глобальных настроек разрешен только пользователям с подтвержденной ролью супер-администратора (проверяется через SQL-функцию или JWT claims).

---

## 2. Безопасность на уровне Frontend и API

1.  **Middleware (Next.js):**
    *   Все маршруты сегмента `/admin/*` (или аналогичного) должны перехватываться Middleware.
    *   При отсутствии сессии или флага администратора происходит немедленный редирект на `/404` или `/unauthorized` (чтобы скрыть сам факт существования панели от обычных пользователей).
2.  **Защита Server Actions и Route Handlers:**
    *   В каждом серверном действии (Server Action) или API эндпоинте обязательно проверяется авторизация и права администратора перед выполнением любой бизнес-логики. Нельзя полагаться только на защиту интерфейса.
3.  **Двухфакторная аутентификация (MFA):**
    *   Рекомендуется требовать MFA при входе в админ-панель для защиты критических клиентских данных.

## 3. Масштабируемая структура и UI/UX панели

Админ-панель должна легко расширяться по мере роста продукта.

### А. Модульная структура разделов (Layout & Navigation)
*   Используйте единый `AdminLayout` с боковой панелью навигации (Sidebar).
*   Структура должна позволять легко добавлять новые страницы (роуты) без изменения ядра панели.
*   Базовые разделы:
    *   **Overview (Дашборд):** Профессиональный дашборд для аналитики продукта (включающий ключевые продуктовые и бизнес-метрики, воронки, графики активности и конверсии).
    *   **Organizations:** Управление клиентами, лимитами и подписками.
    *   **Users:** Управление аккаунтами пользователей.
    *   **Audit Logs:** История действий в системе.
    *   **Settings:** Глобальные настройки платформы.

### Б. Оптимизация больших данных (Таблицы)
*   **Серверная пагинация и фильтрация:** Данные должны запрашиваться порциями. Избегайте выгрузки всей базы на клиент.
*   **Виртуализация:** Для списков с тысячами записей (логи, пользователи) используйте виртуальные скроллеры (например, `@tanstack/react-virtual`), чтобы рендерить только видимые элементы DOM. Это предотвращает зависание браузера.

## 4. Ключевые модули управления

### А. Управление организациями и биллингом
*   **Управление лимитами:** Интерфейс для ручного переопределения квот (дисковое пространство, количество активных проектов/пользователей) для конкретной организации.
*   **Статус подписки:** Просмотр статусов (Active, Past Due, Canceled) и истории транзакций (интеграция со Stripe или аналогичным провайдером).

### Б. Управление пользователями
*   **Имперсонация (Impersonation / "Войти как"):** Критически важная функция для технической поддержки. Позволяет администратору временно сгенерировать сессию от лица пользователя, чтобы увидеть систему его глазами и воспроизвести заявленный баг.
*   **Блокировка (Suspension):** Изменение статуса аккаунта с немедленной инвалидацией текущей сессии пользователя.

### В. История действий (Audit Logs)
*   **Структура таблицы логов:** `id`, `actor_id` (кто сделал), `organization_id`, `action_type`, `entity_id`, `metadata` (прежние и новые значения, IP, User-Agent), `created_at`.
*   **SQL-Триггеры:** Для максимальной надежности логирование критических изменений (смена тарифа, изменение прав) должно выполняться через триггеры PostgreSQL. Это гарантирует запись лога даже при изменении данных в обход API.

## 5. Алгоритм действий при добавлении новых страниц в админку

1.  **Создание роута:** Добавить новую папку в структуру маршрутов (например, `app/(admin)/...`) с файлом `page.tsx`.
2.  **Навигация:** Зарегистрировать новый пункт в массиве конфигурации бокового меню (Sidebar), добавив иконку и проверку прав доступа.
3.  **Компоненты:** Использовать стандартизированные переиспользуемые UI-компоненты панели (Data Table, Page Header, Status Badges) для сохранения визуального единства.
4.  **Безопасность API:** Создать необходимые серверные функции, обеспечив строгую проверку роли администратора внутри каждой функции.
