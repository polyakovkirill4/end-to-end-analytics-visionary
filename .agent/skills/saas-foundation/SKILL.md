# 🏗️ Фундаментальная архитектура SaaS-платформы

Этот навык описывает профессиональные стандарты построения корневой архитектуры SaaS-приложения. Соблюдение этих правил гарантирует безопасность, правильное SEO, удобный UX и масштабируемость платформы для любого B2B проекта.

## 1. Разделение доменов (Коммерческий сайт vs Приложение)

**СТРОГОЕ ПРАВИЛО:** Никогда не смешивай маркетинговый лендинг и само SaaS-приложение в одном проекте/репозитории (если это возможно).

*   **Коммерческий сайт (Лендинг, Блог, SEO):** Основной домен (`domain.com`). Фокус на SEO, скорость, конверсию.
*   **SaaS-платформа (Веб-приложение):** Поддомен (`app.domain.com`). Фокус на безопасность, сложную бизнес-логику, работу с данными.

## 2. Маршрутизация и Главная страница (Root URL)

В проекте веб-приложения (SaaS) **не должно быть коммерческой главной страницы (лендинга)**.

*   Корневой маршрут `/` выполняет функцию **маршрутизатора (Router/Dispatcher)**.
*   **Логика редиректа:**
    *   Если пользователь **АВТОРИЗОВАН** ➡️ редирект на внутреннюю старинцу которую выберет пользователь (или `/dashboard` по умолчанию).
    *   Если пользователь **НЕ АВТОРИЗОВАН** ➡️ редирект на `/sign-in`.

## 3. Middleware: Защита маршрутов и Rate Limiting

Вся логика проверки сессии и защиты роутов должна происходить на уровне Edge через `middleware.ts`.

*   **Публичные маршруты (Public Paths):** Заранее определенный массив путей (например, `['/sign-in', '/sign-up', '/forgot-password']`).
*   **Public Dashboards (Lead Magnets):** Выделенные публичные маршруты для шаринга отчетов (Read-only), изолированные от основной сессии.
*   **Rate Limiting:** Защита публичных и открытых API-маршрутов от спама и DDoS (использование Redis или встроенных лимитов), чтобы защитить БД от парсинга и тяжелых запросов.
*   **Правила Middleware:**
    1.  Проверка сессии: Запрос к провайдеру (Supabase Auth).
    2.  Защита приватных данных: Если сессии нет, а маршрут не публичный ➡️ `/sign-in`.
    3.  Исключение петель: Если сессия есть, попытка зайти на `/sign-in` ➡️ `/dashboard`.

*Критично для производительности:* Middleware не должен применяться к статическим файлам (`_next/static`, картинки, шрифты). Настраивай `matcher` корректно.

## 4. Страницы Аутентификации (Auth Flow) и Маркетинг

*   **Изолированный Layout:** Группа маршрутов `(auth)` имеет свой минималистичный layout без боковых панелей основного приложения.
*   **UTM-Трекинг:** Перехват UTM-меток из URL при первом визите, сохранение их в `localStorage/cookies` и отправка в БД при успешном `sign-up` (необходимо для сквозной аналитики и расчета CAC).
*   **Триггерные E-mail рассылки:** Использование Webhook-ов или событий БД при регистрации для запуска email-цепочек онбординга (через Resend/SendGrid).

## 5. Мультитенантная архитектура (Multi-tenancy) и Изоляция данных

**СТРОГОЕ ПРАВИЛО:** SaaS для B2B должен поддерживать концепцию "Организаций" (Workspaces/Tenants).

*   **Управление организациями:** Пользователь может состоять в нескольких организациях и переключаться между ними.
*   **Изоляция данных (RLS):** В базе данных обязательно использовать Row Level Security (RLS) на основе `organization_id` для предотвращения утечки данных между клиентами.
*   **Soft Deletes (Мягкое удаление):** Строжайший запрет на физическое удаление (`DELETE`) пользователей и организаций. Обязательно использование поля `deleted_at` для предотвращения каскадного обрушения исторических данных.
*   **Data Wipe (GDPR):** Отдельный механизм полного удаления данных клиента по запросу (перевод аккаунта в заморозку и отложенная очистка).

## 6. Маршрутизация Онбординга и Пустые Состояния (Empty States)

*   **Self-Service Onboarding:** После успешной регистрации, если у пользователя нет организации, роутер перенаправляет его на выделенный флоу `(onboarding)` для создания Workspace и подключения первых данных.
*   **Пустые состояния (Empty States):** Если в дашборде/таблице еще нет данных, обязательно показывается красиво оформленная "Заглушка-призыв" (CTA) с кнопкой действия (например, "Подключить источник") или обучающим видео, чтобы не оставлять пользователя на пустом экране.

## 7. Биллинг, Тарифы и Usage-Based Tracking

*   **Интеграция:** Гейтвей оплаты интегрируется через вебхуки на сервере.
*   **Событийный биллинг (Usage tracking):** Логирование тяжелых вычислительных запросов или генерации ИИ-отчетов в БД для тарификации (токены/оплата за действия).
*   **Ограничение доступа (Feature Toggles):** Проверка прав на использование функций происходит на сервере.
*   **UX (Upsell):** При попытке доступа к премиальной функции, вместо системной ошибки, пользователю показывается модальное окно (Paywall) с предложением повысить тариф.

## 8. Ролевая модель и Журнал Аудита (RBAC & Audit Trail)

*   **Локальные роли:** Управление доступом внутри конкретной организации (`admin`, `editor`, `viewer`). Защита UI-элементов и строгая валидация роли на бэкенде.
*   **Журнал Аудита (Audit Trail):** Для B2B сектора критично ведение лога в таблице `audit_logs` для фиксации всех мутаций (кто, когда и что изменил в настройках или правах).

## 9. Архитектура интеграций и Фоновые задачи

*   **Архитектура коннекторов (App Store):** Модульная стандартизация для быстрого добавления новых источников данных (API, OAuth), изоляция логики парсинга.
*   **Фоновые задачи (Background Workers):** Синхронизация данных (ETL) и отправка массовых уведомлений должны быть вынесены в отдельные воркеры (Inngest, Trigger.dev, Cron) вне UI-потока Edge-функций.
*   **Кэширование "тяжелых" расчетов:** Прямой запрет на выполнение тяжелых финансовых расчетов "на лету" в UI-потоке. Использование пред-агрегированных таблиц и фоновых очередей.

## 10. Продуктовая аналитика и Фидбек

*   **Встроенный сбор метрик (Product Analytics):** Обязательная обертка ключевых действий пользователей (PostHog/Mixpanel) для построения воронок использования фич.
*   **Сбор фидбека (Feedback Loop):** Наличие встроенного виджета обратной связи в `(main)` Layout для отправки багов и идей прямо из дашборда.
*   **Флаги функционала (Feature Flags):** Использование тумблеров (LaunchDarkly/БД) для безопасного выкатывания экспериментальных функций только на когорту бета-тестеров.

## 11. Обработка состояний (Loading & Error Boundaries)

*   **Асинхронный UI:** Обязательное использование `Suspense` со Skeleton Loaders для виджетов.
*   **Изоляция ошибок:** Использование `error.tsx` для виджетов дашборда. При падении одного запроса, остальная страница должна работать.
*   **Глобальные страницы ошибок:** Качественно оформленные `not-found.tsx` (404) и `error.tsx` (500).

## 12. Стандарты UI-Layout для SaaS (App Router Layouts)

*   **Структура директорий:** Разделение логики на Route Groups: `(auth)`, `(main)`/`(dashboard)`, `(onboarding)`.
*   **Резиновая верстка:** Главный Layout дашборда адаптируется под экран, строго предотвращая горизонтальный скролл.
*   **Унификация:** Использование единого UI Kit.

## ✅ Чек-лист проверки архитектуры SaaS для Агента

При проектировании или изменении функционала SaaS-платформы, агент обязан проверить:

- [ ] **Безопасность и RLS:** Учитывается ли строгая фильтрация по `organization_id`?
- [ ] **Soft Deletes:** Используется ли `deleted_at` вместо жесткого физического удаления данных?
- [ ] **Middleware & Rate Limit:** Защищен ли роут от спама и неавторизованного доступа?
- [ ] **Empty States & Onboarding:** Есть ли заглушки-призывы (CTA), если данных для отрисовки еще нет?
- [ ] **RBAC & Audit:** Проверяется ли роль перед мутацией и пишется ли действие в `audit_logs`?
- [ ] **Billing & Paywall:** Требует ли новая фича ограничения по тарифу или биллинга за событие? Добавлен ли Upsell?
- [ ] **Background & Caching:** Вынесены ли тяжелые расчеты/ETL в фоновые задачи или кэш?
- [ ] **Ошибки и Загрузка:** Обернут ли тяжелый UI-компонент в `Suspense` со скелетоном и добавлен ли `error.tsx`?
- [ ] **Трекинг & Фидбек:** Отправляются ли метрики (Product Analytics) об использовании новой фичи?
