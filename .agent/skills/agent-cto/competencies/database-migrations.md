# Работа с базой данных Supabase (PostgreSQL)

Этот документ регламентирует стандарты проектирования схем данных, написания SQL-миграций, RLS-политик безопасности и взаимодействия с БД в проекте Visionary.

## 1. Проектирование таблиц и типизация
- **Именование**: Имена таблиц, столбцов, функций и триггеров в БД всегда пишутся в `snake_case`.
- **Идентификаторы**: Уникальные идентификаторы (`id`) записей должны использовать UUID v4 (по умолчанию в PostgreSQL устанавливается `gen_random_uuid()`).
- **Служебные поля**: Каждая таблица обязана содержать столбцы:
  - `created_at timestamptz DEFAULT now()`
  - `updated_at timestamptz DEFAULT now()`
- **Связь с организациями**: Практически все таблицы данных (транзакции, лиды, метрики) должны иметь внешний ключ `organization_id` для разграничения доступа между клиентами SaaS.

## 2. Безопасность (Row Level Security - RLS)
- RLS должна быть принудительно включена на ВСЕХ таблицах БД (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`).
- Доступ пользователей к данным должен быть ограничен их принадлежностью к организации. Пример типичной политики для чтения:
  ```sql
  CREATE POLICY "Users can read data in their organization" ON public.transactions
  FOR SELECT USING (
    organization_id IN (
      SELECT org_id FROM public.organization_members WHERE user_id = auth.uid()
    )
  );
  ```
- Для суперпользователей / администраторов должна быть предусмотрена роль impersonation или специальный обход RLS (проверяется через `auth.jwt()`).

## 3. SQL-миграции и изменения схем
- Все изменения структуры БД описываются в виде SQL-файлов миграций.
- Изменения должны быть обратно совместимы (не ломать работающее приложение в продакшене).
- При добавлении новых полей задавай дефолтные значения или разрешай `NULL` для предотвращения ошибок со старыми записями.
- **Индексы**: Создавай индексы для полей, по которым часто происходит фильтрация или объединение (`organization_id`, `created_at`, внешние ключи).

## 4. Транзакции и RPC
- Финансовые транзакции, списания баланса, изменения статуса подписки и групповые обновления данных должны выполняться атомарно.
- Для выполнения сложных многошаговых операций в БД используй Postgres Functions (RPC) в Supabase, вызывая их через `.rpc('function_name')` в клиенте.
- Физическое удаление данных запрещено. Используй Soft Delete через флаг `is_active: false` или поле `deleted_at timestamptz`.
