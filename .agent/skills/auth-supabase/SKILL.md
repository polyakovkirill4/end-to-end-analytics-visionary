## 1. Схема Данных и Архитектура (PostgreSQL + Supabase)

Система построена на разделении сущностей пользователей и организаций (B2B SaaS). Реализуй взаимодействие со следующей структурой:

### Таблица `profiles` (Профили пользователей)
- `id` (uuid, primary key, references `auth.users`)
- `first_name` (text, обязательное)
- `last_name` (text, обязательное)
- `email` (text, обязательное)
- `organization_id` (uuid, references `organizations`, nullable)
- `role` (text, значения: `'owner'`, `'admin'`, `'member'`, по умолчанию `null`)

### Таблица `organizations` (Организации/Компании)
- `id` (uuid, primary key)
- `name` (text, обязательное)
- `slug` (text, уникальное, обязательное)
- `created_at` (timestamp)
- `created_by` (uuid, references `auth.users`)

## 2. Сервис Авторизации (`services/authService.ts`)

Все операции с Supabase Auth инкапсулируются внутри `authService`. Используй клиент `@/lib/supabase/client`.

### Обязательные функции и правила:

1. **Регистрация (`signUp`)**:
   - Принимает `email`, `password`, `first_name`, `last_name`.
   - Передает `first_name` и `last_name` в `options.data` (user metadata).
   - **Отказоустойчивость (Fallback)**: Если стандартный триггер создания профиля в БД возвращает ошибку (код 500/база данных), поймай ошибку, выполни повторную регистрацию или принудительно обнови профиль через метод `updateUserProfile` для исключения рассинхронизации.

2. **Вход (`signIn`)**:
   - Принимает `email`, `password`. Возвращает сессию.

3. **Выход (`signOut`)**:
   - Всегда вызывай `supabase.auth.signOut({ scope: 'local' })`. Это очищает локальную сессию на текущем устройстве, не сбрасывая сессии пользователя на других устройствах.

4. **Восстановление пароля (`resetPassword` и `updatePassword`)**:
   - **Запрос ссылки**: `supabase.auth.resetPasswordForEmail(email, { redirectTo: `${window.location.origin}/update-password` })`.
   - **Обновление пароля**: `supabase.auth.updateUser({ password })`.

## 3. Контекст Авторизации (`context/AuthContext.tsx`)

Обеспечивает глобальное состояние аутентификации и мгновенный рендеринг интерфейса.

- **Shell First Approach (Кэширование)**:
  - Профиль пользователя кэшируется в `localStorage` под ключом `app_cached_profile`.
  - При инициализации стейт `profile` моментально заполняется данными из кэша. Асинхронный запрос к Supabase для проверки актуальности сессии выполняется в фоне.
- **Интеграция с БД**:
  - При получении `session.user` контекст запрашивает запись из таблицы `profiles` для получения `role` и `organization_id`. Данные обновляют стейт и перезаписывают `app_cached_profile`.
- **Подписка на события (`onAuthStateChange`)**:
  - `SIGNED_IN` / `TOKEN_REFRESHED`: Загрузка профиля из БД, обновление стейта и кэша.
  - `SIGNED_OUT`: Сброс `user`, `profile`, `session` в `null`. Полное удаление `app_cached_profile` и очистка системных ключей Supabase (`sb-*-auth-token`) из `localStorage` и `sessionStorage` во избежание «фантомных» сессий.
  - `PASSWORD_RECOVERY`: Перенаправление пользователя на страницу `/update-password`.

## 4. B2B Flow: Управление Организациями и Защита Маршрутов

В SaaS-модели пользователь должен принадлежать организации для работы внутри дашбордов.

### Создание Организации (Flow):
1. Если пользователь успешно зарегистрирован и авторизован, но `profile.organization_id === null`, он блокируется на этапе роутинга и принудительно перенаправляется на `/create-org` (или `/sign-up-org`).
2. На странице создания организации пользователь вводит `name` (название компании). `slug` генерируется автоматически.
3. **Транзакционная логика создания**:
   - Шаг 1: Создается запись в таблице `organizations` (указывается `name`, `slug`, `created_by`).
   - Шаг 2: Полученный `organization_id` записывается в профиль текущего пользователя (`profiles`), а поле `role` обновляется до значения `'owner'`.
   - Шаг 3: Обновляется `AuthContext` (стейт и локальный кэш), после чего открывается доступ к дашборду `/dashboard`.

### Защита роутов на сервере (`middleware.ts`) и клиенте
- **Серверная защита (`src/middleware.ts`)**: Обязательная проверка сессии/токена (`supabase.auth.getUser()`) для всех приватных маршрутов (`/dashboard/*`, `/settings/*`) с использованием `@supabase/ssr`. При отсутствии сессии — редирект на `/sign-in`.
- **Проверка организации**: Доступ к дашбордам разрешен только при наличии валидной сессии **И** установленного `organization_id` в профиле пользователя. При отсутствии `organization_id` — жесткий редирект на `/create-org` (на уровне серверного Layout/HOC или внутри middleware).

## 5. Файловая структура и Архитектура (Next.js 15 App Router)

Для корректной работы маршрутизации, агент должен создавать файлы по следующим путям (группа `app/(auth)`):

- `src/app/(auth)/layout.tsx` — Общий Layout для аутентификации (Server Component).
- `src/app/(auth)/loading.tsx` — Состояние загрузки (спиннеры/скелетоны).
- `src/app/(auth)/sign-in/page.tsx` — Страница входа.
- `src/app/(auth)/sign-up/page.tsx` — Регистрация нового аккаунта.
- `src/app/(auth)/sign-up-org/page.tsx` — Создание первой организации (B2B onboarding).
- `src/app/(auth)/forgot-password/page.tsx` — Запрос ссылки для сброса пароля.
- `src/app/(auth)/update-password/page.tsx` — Установка нового пароля по ссылке из email.
- `src/app/(auth)/verify-email/page.tsx` — Экран "Проверьте почту" после успешной регистрации.
- `src/app/(auth)/auth-error/page.tsx` — Обработка ошибок авторизации (сообщения об ошибках OAuth, устаревшие ссылки и т.д.).
- `src/app/(auth)/join/[token]/page.tsx` (или папка `join`) — Обработка ссылки-приглашения в организацию.

## 6. UI-стандарты и Дизайн-паттерны

1. **Server Components vs Client Components**:
   - Layout-файлы (`layout.tsx`) и страницы-контейнеры (`page.tsx` без интерактивности) должны быть **Server Components**.
   - Формы авторизации, кнопки submit и хуки управления состоянием должны быть вынесены в отдельные компоненты с директивой `'use client'`.

2. **Стандартный UI Дизайн (Split Screen Layout)**:
   - Все страницы аутентификации должны следовать паттерну разделенного экрана.
   - **Левая часть (или центральная карточка на мобильных)**: Поля ввода, основная информация, сообщения об ошибках и кнопки действий. Фон светлый/белый.
   - **Правая часть**: Контент о нашем сервисе (любом разрабатываемом сервисе). Это может быть премиальный фон, паттерны, отзывы клиентов, USP продукта. Это создает ощущение профессионального дорогого SaaS.

## 7. Валидация Форм и UI Элементы (`react-hook-form` + Zod/Кастомная валидация)

Все UI-страницы (`/sign-in`, `/sign-up`, `/forgot-password`, `/update-password`, `/create-org`) должны соответствовать строгим критериям проверки данных.

### Критерии валидации:
- **Обязательные поля**: `email`, `password`, `first_name`, `last_name`, `org_name` не могут быть пустыми. Поля должны очищаться от пробелов по краям (`.trim()`).
- **Проверка Email**: Строгое соответствие регулярному выражению электронной почты.
- **Проверка Пароля**:
  - Минимальная длина — 8 символов.
  - Обязательное наличие как минимум одной заглавной буквы, одной строчной буквы и одной цифры.
- **Отображение ошибок**: Все ошибки валидации (как со стороны клиента, так и ответы от API Supabase) должны выводиться точечно под соответствующим полем ввода с помощью компонента `<FieldError />`. Кнопка отправки формы должна переходить в состояние `disabled` на время выполнения запроса.
