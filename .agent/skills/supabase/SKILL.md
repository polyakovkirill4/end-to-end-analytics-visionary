Твоя задача — проектирование схем баз данных, написание SQL-миграций, настройка политик безопасности RLS и интеграция бизнес-логики с сервисами Supabase в нашем проекте.

## 1. Стандартная структура таблиц (Обязательные поля)

Любая таблица в базе данных должна проектироваться по следующим строгим правилам:
- **Регистр**: Имена таблиц и колонок пишутся строго в `snake_case`.
- **Идентификатор (ID)**: Первичный ключ `id` ВСЕГДА должен иметь тип `uuid` и значение по умолчанию `gen_random_uuid()`. Запрещено использовать автоинкрементные целые числа (serial/bigserial).
- **Временные метки (Timestamps)**: Каждая таблица обязана содержать колонки времени:
  - `created_at timestamptz not null default now()` — дата создания записи.
  - `updated_at timestamptz not null default now()` — дата последнего изменения (обновляется через триггер).
- **Аудит (Кто создал / обновил)**: В большинстве таблиц (кроме системных и связующих) необходимо отслеживать авторство:
  - `created_by uuid references auth.users(id)` — кто создал запись.
  - `updated_by uuid references auth.users(id)` — кто последним изменил запись.

## 2. Авторизация и RBAC (Role-Based Access Control)

Не нужно усложнять саму авторизацию: мы используем встроенную систему **Supabase Auth** для базового входа и сессий. Однако сама логика прав и разрешений строится на кастомном RBAC.

- **Связь с профилями**: Данные пользователя хранятся в публичной таблице `profiles` (связь 1 к 1 с `auth.users`).
- **Таблицы ролей и разрешений**: Роли мы должны создавать сами руками. Для этого создаются таблицы ролей (`roles`), разрешений (`permissions`) и их связок (`role_permissions`, `user_roles`).
- Это позволяет гибко прописывать уникальные роли и свои разрешения для каждого типа пользователей в проекте.

## 3. Безопасность на уровне строк (RLS - Row Level Security)

**Создание любой таблицы без включения и настройки политик RLS строго запрещено.** RLS-правила надо прописывать ВСЕГДА на таблицах, чтобы корректно работала безопасность.

### Включение RLS:
```sql
alter table public.имя_таблицы enable row level security;
```

### Написание политик (Policies):
Политики должны использовать наши таблицы RBAC (`user_roles`, `roles`) для разграничения доступа:
```sql
create policy "Admins can do everything"
on public.имя_таблицы for all
to authenticated
using (
  exists (
    select 1 from public.user_roles ur
    join public.roles r on r.id = ur.role_id
    where ur.user_id = auth.uid() and r.name = 'ADMIN'
  )
);
```

## 4. Индексы для оптимизации производительности

Смотря какие условия и какая таблица используется, в идеале нужно прописывать индексы для нужных таблиц, чтобы искать данные быстрее.

1. **Внешние ключи (Foreign Keys)**: PostgreSQL не создает индексы автоматически для связей. Создавай индексы для полей, по которым будут происходить `JOIN`:
   ```sql
   create index имя_таблицы_имя_колонки_idx on public.имя_таблицы (имя_колонки_id);
   ```
2. **Поля частой фильтрации и поиска**: Добавляй индексы для полей, по которым часто делаются запросы (например, фильтры `.eq()`, диапазоны дат `created_at`).
3. **Уникальные индексы**: Для защиты от дублирования данных на уровне БД:
   ```sql
   create unique index unique_client_group_idx on public.client_groups (client_id, group_id);
   ```

## 5. Рекомендации по типам данных

- **Уникальные ключи**: `uuid`.
- **Денежные суммы**: `numeric(12, 2)` или `integer` (в копейках) — *использование float/double precision запрещено*.
- **Сложные структуры данных**: `jsonb` для гибких настроек или метаданных.
- **Списки статусов**: SQL-перечисления (`ENUM`) для жестко заданных состояний (например, `new`, `in_progress`, `converted`).
